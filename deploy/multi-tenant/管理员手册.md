# 管理员手册

这份手册面向**运维这套多租户部署的人**。所有命令都在部署机上执行，本文里的输出是实测结果，不是示意。

```bash
ssh root@<部署机>
cd /home/dsh-mt
```

管理员目前通过命令行操作，没有 Web 控制台。管理动作分四类：**租户生命周期**、**模型策略**、
**日常巡检**、**备份恢复**。

---

## 1. 一分钟上手

```bash
bin/mt.sh list        # 有哪些租户、各自入口端口和用户
bin/mt.sh ps          # 容器状态
bin/mt.sh usage       # 每个租户用了多少模型额度
bin/mt.sh doctor      # 全面自检；出问题先跑这个
```

任何一条命令加 `-h` 或直接不加参数都会打印用法。命令清单也在 `bin/mt.sh` 头部的注释里。

**管理员要做的四件事**：

| 场景 | 去哪一节 |
|---|---|
| 有人要开账号 / 离职要停号 | §2 租户生命周期 |
| 换模型、加模型、看谁用了多少 | §3 模型管理 |
| 每天/每周看一眼系统是否正常 | §4 日常巡检 |
| 出事前的保命措施 | §5 备份与恢复 |
| 已经出事了 | §6 故障排查 |

## 2. 租户生命周期

### 2.1 新增租户

```bash
bin/mt.sh add <租户id> --user <用户名> [--title "显示名"] [--node <节点>]
bin/mt.sh up
bin/mt.sh url
```

`<租户id>` 用小写字母、数字和短横线（`^[a-z][a-z0-9-]{1,30}$`）。命令会打印**初始密码**，
只显示这一次，请立刻交给该租户并让他自己记好（目前租户不能自助改密码，见 §7）。

实测输出：

```
$ bin/mt.sh add demo --user lisi --title "演示租户"
added tenant demo (node: local)
  user:     lisi
  password: <12 位随机密码，本文遮蔽>

$ bin/mt.sh up
rendered docker-compose.yml for 5 tenant(s): alpha, beta, gamma, delta, demo
 Container mt-dsh-demo  Creating
 Container mt-dsh-demo  Created
 Container mt-dsh-demo  Starting
 Container mt-dsh-demo  Started
    已注册 5 个租户
```

端口是自动分配的（内部端口 3181 起、入口端口 8091 起），不需要你操心：

```
$ bin/mt.sh list
alpha	节点=local	内部端口=3181	入口端口=8091	用户=alice	主机=alpha.dsh.local
beta	节点=local	内部端口=3182	入口端口=8092	用户=bob	主机=beta.dsh.local
gamma	节点=local	内部端口=3183	入口端口=8093	用户=carol	主机=gamma.dsh.local
delta	节点=local	内部端口=3184	入口端口=8094	用户=dave	主机=delta.dsh.local
demo	节点=local	内部端口=3185	入口端口=8095	用户=lisi	主机=demo.dsh.local
```

**新增后一定要验证一次**，确认这个租户真的能登录：

```bash
bin/mt.sh accept --tenant demo --user lisi --password <初始密码>
```

期望结尾是 `结果：11 通过，0 失败`。

### 2.2 改密码

```bash
bin/mt.sh passwd <租户> <用户>              # 随机生成新密码
bin/mt.sh passwd <租户> <用户> --password <新密码>   # 指定新密码
```

实测：改完立刻生效——新密码登录返回 303（成功跳转），旧密码返回 401。

```
用新密码登录: HTTP 303
用旧密码登录: HTTP 401
```

⚠️ **改密码不会踢掉已经登录的会话**。对方的浏览器只要还开着，就仍然能用。要强制下线，
目前只能 `bin/mt.sh restart <租户>`（会中断该租户正在跑的对话）。

### 2.3 重启

```bash
bin/mt.sh restart <租户>   # 只重启一个租户
bin/mt.sh restart          # 重启所有租户（会重新注册运行时）
```

重启会换掉 DSH 的启动 token，命令会自动重新注册，正常情况下不需要你额外做什么。

### 2.4 停用与启用

```bash
docker stop mt-dsh-<租户>                          # 临时停掉（数据不动）
docker start mt-dsh-<租户> && bin/mt.sh register <租户>
```

实测：停掉后租户访问得到 **HTTP 502**（网关连不上已注册的运行时）；重新启动并注册后恢复 **200**。

> **502 与 503 的区别，排查时很有用**：
> - **502** = 运行时已注册但连不上 → 容器停了、崩了，或地址变了。
> - **503** = 从来没有注册，或已被摘掉 → 容器没起来，或者 `bin/mt.sh remove` 之后。

### 2.5 删除租户

```bash
bin/mt.sh remove <租户>            # 删容器和注册表条目，数据保留
bin/mt.sh remove <租户> --purge    # 连数据一起删（不可恢复）
```

实测输出：

```
$ bin/mt.sh remove demo
its data stays under tenants/demo/ — delete that directory to erase it
==> 停止并删除容器 mt-dsh-demo
    数据保留在 tenants/demo/（要删除加 --purge）
    网关会在 2 秒内摘掉该租户，无需重启
```

**删除前建议先备份**（§5）。删掉之后，该租户的所有会话、工作区文件都还在
`tenants/<租户>/` 下，可以随时手工取回。

## 3. 模型管理

### 3.1 分工

| 谁 | 做什么 |
|---|---|
| 管理员 | 统一配置私有化部署的模型（哪些模型可用、走哪个网关、真 key 是什么） |
| 租户 | 在对话界面的**模型选择器**里挑一个，不需要也不应该碰凭据 |

真 key 只存在于模型网关容器里，租户容器里拿到的是**占位 key**（形如 `sk-mt-alpha-…`），
即使租户把自己的容器翻个底朝天也拿不到真凭据。所有调用经 `mt-model-gateway` 转发，
因此**用量天然可按租户核算**。

### 3.2 租户看到什么

实测一个租户能拿到的模型目录：

| 项 | 值 |
|---|---|
| 默认 | `deepseek-official` / `deepseek-flash` |
| 分组 | DeepSeek |
| 模型 | **DeepSeek-V41-Flash** |

也就是说：**管理员配好之后，租户打开对话界面就能在模型选择器里看到并切换**。

> 注意：设置面板里的「模型」页面在远程浏览器上是**不可用**的，这是 DSH 的设计
> （非 loopback 页面不提供持久化设置读写）。租户选模型的正确位置是**对话框**里的模型选择器。
> 管理员若需要那个设置页面，用 SSH 隧道把运维端口映射到本机后访问：
> `ssh -L 8099:127.0.0.1:8099 root@<部署机>`，然后浏览器开 `http://127.0.0.1:8099`。

### 3.3 调整模型策略

```bash
vi model.patch.yml      # 声明共享给所有租户的模型（与 cordis.patch.yml 同样的 YAML 格式）
vi model.env            # 该模型需要的凭据
bin/mt.sh model         # 应用到全部租户并重启
```

`bin/mt.sh model` 会把这段配置**拼接（splice）**进每个租户的 profile patch，用注释标记包起来，
所以反复执行不会重复插入，也不会覆盖租户自己的设置。

### 3.4 用量核算

```bash
bin/mt.sh usage                      # 全部租户汇总
bin/mt.sh usage --tenant alpha       # 单个租户
bin/mt.sh usage --tail 200           # 看最近 200 条明细
```

实测输出：

```
租户      调用   输入token  输出token  命中缓存  平均耗时
alpha        24       4258        222     76288    1833ms
delta         3        680        357     12800    1322ms
----------------------------------------------------------
合计          27       4938        579     89088

被拒绝或失败的请求 25 条（未知 key、上游错误等）
  2026-10-01T15:44:54.938Z  -  HTTP 401  unknown-or-missing-key
```

**「被拒绝的请求」要留意**：正常应该是 0 或个位数。持续出现 `unknown-or-missing-key`
说明有东西在拿错误凭据调用模型网关（多半是有人手工 curl 或某个租户的配置被改坏了）。

原始日志在 `logs/model-usage.jsonl`（每次调用一行）。

## 4. 日常巡检

```bash
bin/mt.sh doctor        # 一次跑完 60 项检查
```

期望：`0 项失败`。有警告（warn）不一定是故障，但要读一遍原因。

其余常用：

```bash
bin/mt.sh runtimes      # 控制面认识哪些运行时（每个租户都应在列）
bin/mt.sh ps            # 容器是否都在跑
bin/mt.sh usage         # 额度消耗
df -h /home             # 空间
```

**建议的巡检节奏**：每天看一眼 `doctor` 结论和 `usage` 的拒绝计数；每周看一次磁盘。

### 4.1 接进 Prometheus

控制面暴露 `GET /__mt/metrics`（Prometheus 文本格式）。本机（loopback）抓取免密钥；跨机抓取要带
密钥——**用 Bearer**，因为 Prometheus 发不了自定义请求头：

```yaml
# prometheus.yml
scrape_configs:
  - job_name: dsh-multitenant
    scheme: https
    metrics_path: /__mt/metrics
    tls_config:
      insecure_skip_verify: true      # 自签证书；也可用 ca_file 指向 state/tls/ca.crt
    authorization:
      type: Bearer
      credentials_file: /etc/prometheus/dsh-multitenant.token   # 内容是 state/registry.key
    static_configs:
      - targets: ['<控制面地址>:8090']
```

现成的两个文件在 `alerts/` 下，直接用：

| 文件 | 用途 |
|---|---|
| `alerts/prometheus-scrape.yml` | 抓取配置片段（填上地址即可） |
| `alerts/mt-alerts.yml` | **10 条告警规则**，含每条"看到之后做什么" |

```bash
promtool check rules  alerts/mt-alerts.yml     # 校验规则
promtool check config prometheus.yml           # 校验整体配置
curl -X POST http://<prometheus>:9090/-/reload # 热加载（需 --web.enable-lifecycle）
```

### 4.2 接进这台机器上已有的 Prometheus

这台机器上跑着另一套 Prometheus（`capex-ai-lab-prometheus-1`），本部署的告警可以直接接进去：

```bash
bin/mt.sh wire-prometheus --check     # 看现在接得怎么样
bin/mt.sh wire-prometheus             # 接入（幂等，可重复执行）
bin/mt.sh wire-prometheus --remove    # 撤掉（从自动备份恢复）
```

它做三件事：把注册密钥放到对方**已挂载**的目录里（容器内是 `/prometheus/dsh.token` ✓）、
往对方的 `prometheus.yml` 追加抓取任务 ✓、把 `alerts/mt-alerts.yml` 的规则追加到对方的规则文件 ✓。
每一步都先备份 ✓，并且**先用 promtool 校验、通过才写线上文件** ✓ —— 校验不过就原样退出 ✓。

**两个踩过的坑**（脚本里都处理了，换台机器重做时会遇到）：

1. **那两个文件是单文件绑定挂载** ✗ —— 用 `cp` 覆盖会**换掉 inode** ✓，容器里仍然指向旧 inode ✓，
   表现是"文件改了、容器看不到"，且**没有任何报错** ✓。必须**原地写**（`cat 源 > 目标` ✓）。
   如果之前被 `cp` 破坏过，只能**重启容器**重新建立挂载 ✓（实测 2 秒 ✓）。
2. **追加抓取任务时列表项缩进要一致**（他们文件里是 2 空格 ✗）—— 缩进错了 YAML 直接解析失败 ✓，
   靠 promtool 在上线前拦住 ✓。

**别用域名当抓取目标** ✓：这台机器的 **Docker 内嵌 DNS 有超时问题** ✗（日志里
`127.0.0.11:53 i/o timeout` ✓，导致 `contextforge`、`nacos` 都是 down ✗）。脚本用 **IP** ✓，
不受它影响 ✓。

**实测结果**：10 条规则加载 ✓、抓取目标 `up` ✓、15 类 `mt_` 指标进入他们的 Prometheus ✓、
四个租户的就绪值都是 1 ✓、他们原有的 5 个任务不受影响 ✓；重复执行不会重复添加 ✓。

| 告警 | 触发条件 | 严重度 |
|---|---|---|
| `DshTenantNotReady` | 某租户运行时不就绪 5 分钟 | critical |
| `DshNoTenantReady` | 所有租户都不就绪 10 分钟 | critical |
| `DshControlPlaneDown` | 抓不到控制面 3 分钟 | critical |
| `DshTenantRegisteredButNoToken` | 注册了但没拿到启动 token | warning |
| `DshModelRequestsRejected` | 15 分钟内有模型请求被拒（限额或 key 错） | warning |
| `DshModelRequestsUnattributed` | 有请求未能归属到租户（key 配错） | warning |
| `DshBackupStale` | 备份超过 48 小时未成功 | warning |
| `DshTenantMissing` | 指标里的租户数与注册表不一致 | warning |
| `DshDeployDiskFillingUp` | 按趋势预计 24 小时内剩余 <5GB | warning |
| `DshDeployDiskCritical` | 分区剩余 <2GB | critical |

后两条依赖 node_exporter（走它的 `node_filesystem_*`），其余只依赖控制面自己的指标。

**实测**：用一个临时 Prometheus 抓过——目标 `up`、抓到 14 类 `mt_` 指标、四个租户的就绪值都是 1、
10 条规则全部加载且正常状态下为 `inactive`；故意把密钥改错后抓取报 `401 Unauthorized`、
`health` 变 `down`（**失败是可见的，不是静默无数据**）。

可用指标：`mt_tenant_registered`、`mt_tenant_ready`、`mt_tenant_has_token`、`mt_tenant_info`、
`mt_tenant_model_calls_total`、`mt_tenant_model_input_tokens_total`、
`mt_tenant_model_output_tokens_total`、`mt_tenant_model_cache_read_tokens_total`、
`mt_tenant_model_rejected_total`、`mt_tenant_model_limit_rpm`、
`mt_tenant_model_limit_daily_tokens`、`mt_gateway_uptime_seconds`、`mt_gateway_tenants`、
`mt_gateway_edge_port`、`mt_gateway_admin_actions_total`、
`mt_backup_last_success_timestamp_seconds`、`mt_model_unattributed_requests_total`。

用量类计数来自模型网关的用量日志（含轮转出去的历史文件），因此与控制台、`bin/mt.sh usage`
对得上；日志轮转丢掉最旧一代时，这些计数会随之回退。

## 5. 备份与恢复

> **恢复会用归档里的 `.env` 覆盖当前的 `.env`** ✗ —— 备份**之后**新增或改过的配置项会丢，
> 而且**不会有任何提示** ✓（实测踩到：给节点代理配的 `MT_NODE_AGENT_URL` 在一次恢复后消失，
> 表现为控制台的运维操作全部报"节点上没有在跑的代理"）。
> **恢复后要检查 `.env`**：`MT_NODE_AGENT_URL`、`MT_TENANT_NETWORKS`、`MT_EGRESS_ALLOW`、
> 模型凭据这些是否还在，然后 `bin/mt.sh render` + `bin/mt.sh up` 让改动生效。
> 归档里的 `.env` 是打包那一刻的副本 ✓，所以恢复等于把配置也回退到那一刻 ✓。

### 5.1 备份

```bash
bin/mt.sh backup              # 全部租户数据 + 控制面状态
ls -lh backups/
```

备份是**冻结快照**：归档前会短暂停写以保证一致性，并把每个租户的数据量、会话数写进
`MANIFEST.txt`：

```
DSH 多租户部署备份
时间        : 20261002T020422Z
一致性      : 冻结快照
租户        : alpha beta gamma delta
运行时镜像  : dsh-web:local-20261001T1440
各租户数据量:
  alpha  home=552K  workspace=20K  会话=25
包含内容: tenants/ state/ tenants.json .env
未包含  : image-overlay/（可由源码重建）、backups/、logs/
```

归档权限是 `600`（含所有租户的会话与凭据），**转移时请走加密通道**，不要丢在共享目录里。

### 5.2 恢复

```bash
bin/mt.sh restore backups/dsh-mt-<时间戳>.tar.gz
bin/mt.sh up
```

恢复是**非破坏性**的：现有数据先整体挪到 `restore-aside-<时间戳>/`，不会直接删除。
确认新数据没问题后，再手工删掉那个目录。

只想恢复会话数据、保留当前配置（比如恢复到一个改了模型配置的环境）：

```bash
bin/mt.sh restore <归档> --data-only
```

只想恢复**某一个租户**（其它租户、注册表、控制面配置都不动，也不需要停整套）：

```bash
bin/mt.sh restore <归档> --tenant gamma      # 只动 gamma
bin/mt.sh restart gamma                      # 然后重启它
```

现有数据不会被删：会挪到 `restore-aside-<时间戳>/tenants/<租户>/`，确认无误后自行删除。

### 5.3 定时备份

`bin/mt.sh up` 会一并启动 `mt-backup` 服务（控制面上），它按下面的配置自动备份：

| 变量（写在 `.env`） | 默认 | 含义 |
|---|---|---|
| `MT_BACKUP_INTERVAL_SECONDS` | 86400 | 间隔秒数（一天一次） |
| `MT_BACKUP_KEEP` | 7 | 保留最近几份，更旧的自动删除 |

它跑的就是你手工跑的同一个 `bin/backup.sh`，所以两种方式不会跑偏。日志：`docker logs mt-backup`。

## 5.4 控制面高可用（备用实例）

控制面是整套部署的单点：它挂了，所有租户都不通。可以用**主备两个实例共享同一份 `state/`** 来消除进程级故障，但要清楚它能解决什么、不能解决什么。

**已经具备的前提**（都是为这件事准备的）：

- 会话签名密钥在 `state/session.key`、管理员密钥在 `state/admin.key`，**不是进程内存**——所以另一个实例能验证主实例签发的会话；
- 运行时注册表在 `state/runtimes.json`、租户注册表在 `tenants.json`，都是共享文件；
- 网关带 Docker healthcheck，进程卡死会被自动重启。

**实测确认过的性质**：在同一台机器上再起一个共享 `state/` 的实例，用主实例签发的**管理员会话**访问它的控制台与 API 都是 200，**租户会话**访问工作区也是 200——两边认同一份会话。

**怎么做主备**：

```bash
# 备用机器上：同一份项目、同一份 state/ 与 tenants.json（定期同步）
rsync -a --delete <主控>:/home/dsh-mt/state/      /home/dsh-mt/state/
rsync -a <主控>:/home/dsh-mt/tenants.json         /home/dsh-mt/tenants.json

# 备用实例：不抢租户专属入口端口（那些端口属于主实例）
docker run -d --name mt-gateway-standby --network host \
  -v /home/dsh-mt/tenants.json:/config/tenants.json \
  -v /home/dsh-mt/state:/state -v /home/dsh-mt/logs:/logs \
  -e MT_EDGE_PORT=8090 -e MT_EDGE_LISTEN=0 mt-gateway:local
```

切换由你把**虚拟 IP 或 DNS** 指向备用机（这是宿主/网络层的动作，本部署不替你做）。

**它不能解决的**：主机宕机、磁盘损坏、`state/` 本身的丢失——所以 §5 的备份仍然是必须的。切换前建议先确认备用实例的 `/__mt/health` 是 200、并且 `bin/mt.sh runtimes` 里四个租户都在。

实测（在副本里验证过）：归档校验、挪开旧数据、解包、`--data-only` 时保留当前
`state/`、`tenants.json`、`.env`，把归档版本放到 `*.aside-restored` —— 全部按预期工作。

## 5.5 离线环境的镜像与升级

内网没有互联网，**`docker pull` 到不了任何地方**，所以镜像必须先在本机或内网仓库里。

### 5.5.1 把镜像推进内网仓库（Harbor）

```bash
# .env 里配置一次：
#   MT_REGISTRY_HOST=127.0.0.1:18083      # 本机 Harbor 的 nginx 端口
#   MT_REGISTRY_PROJECT=dsh
#   MT_REGISTRY_USER=<你的账号>
#   MT_REGISTRY_PASSWORD=<你的密码>
#   MT_REGISTRY_PLAIN_HTTP=1              # 仓库是明文 http 时才需要
bin/mt.sh registry-push                   # 推运行时镜像 + 四个控制面/节点镜像
bin/mt.sh registry-push --tag 20261003    # 指定标签
bin/mt.sh registry-push --host <仓库> --project dsh --runtime-only
```

推送的是：`dsh-web`（租户运行时）+ `mt-gateway`、`mt-egress-proxy`、`mt-model-gateway`、
`mt-node-agent`。**没有仓库配置时它会直接报错并给出该配什么**，不会静默跳过。

> 明文 http 的仓库需要把地址加进 `/etc/docker/daemon.json` 的 `insecure-registries` 并重启
> docker，脚本会检查并提示。

**如果连仓库也没有**，用文件搬运：

```bash
docker save dsh-web:local-<标签> | gzip > dsh-web.tar.gz     # 在有网的机器上
docker load -i dsh-web.tar.gz                                 # 在目标机器上
```

### 5.5.2 滚动升级（一次一个租户）

```bash
bin/mt.sh upgrade --status                          # 先看各租户当前用的镜像
bin/mt.sh upgrade --image dsh-web:local-<新标签> --dry-run   # 看会做什么，不改动
bin/mt.sh upgrade --image <新镜像>                  # 逐个租户升级
bin/mt.sh upgrade --image <新镜像> --tenants delta  # 先只升一个（推荐）
bin/mt.sh upgrade --image <新镜像> --tenants delta \
  --verify-model "delta:dave:<密码>"                # 额外做一次真实模型调用
```

**它的安全语义**（实测过）：

- 每个租户升级后，等**控制面把它判为 ready**（网关实测连得上且持有启动 token）再换下一个；
- 任何一个租户起不来，**把它换回旧镜像并立刻停止**，后面的租户不受影响、仍在旧镜像上服务；
- 全部成功后才把新镜像写进 `.env`（这样下次 `up`/重建也用它）。

实测：坏镜像（跑不了 `dsh` 的镜像）被检测出来，该租户自动回滚、恢复可用，其余三个租户全程未受
影响；冒烟 15/15、验收 11/11 保持通过。

**手工回滚**：把 `.env` 里的 `DSH_IMAGE` 改回旧标签，然后
`bin/mt.sh up`（或 `bin/mt.sh upgrade --image <旧镜像>`）。

### 5.5.3 升级检查清单

1. 新镜像已在**本机**或内网仓库里（`docker images | grep dsh-web`）；
2. `bin/mt.sh backup`——升级前有一份可回退的数据；
3. 先 `--tenants <一个租户>` + `--verify-model` 验证；
4. 通过后再 `bin/mt.sh upgrade --image <新镜像>` 升其余；
5. 升完 `bin/mt.sh doctor` + `bin/mt.sh smoke` 确认整体正常。

**注意**：升级会重建租户容器，**IP 与启动 token 都会变**，脚本会自动重新注册；如果你是手工
`docker-compose up -d dsh-<租户>`，记得补一次 `bin/mt.sh register <租户>`。

### 5.5.4 一个反复踩到的坑：`up` 不会重建镜像

`bin/mt.sh up` 启动容器时**不会重新构建镜像**——它用的还是本机已有的 `mt-gateway:local` 等。
改了 `gateway/`、`node-agent/`、`egress-proxy/` 下的代码之后只跑 `up`，容器里跑的**还是旧代码**，
表现为"新加的功能不存在"或"按钮没反应"，很容易误判成代码有问题（我在开发控制台时踩了两次）。

改完这些目录的代码后要显式重建：

```bash
docker-compose build gateway node-agent egress-proxy model-gateway
bin/mt.sh up
```

只改了 `bin/` 下的脚本（`mt.sh`、`disk.sh`、`backup.sh` …）**不需要重建**：那些脚本是**挂载**进
容器的（`.:/project`），改完立即生效。

改了 `bin/render.js` 之后要 **`bin/mt.sh render`**（或 `up`）重新生成 `docker-compose.yml`
——比如新增了环境变量，不重新渲染就不会进到容器里。

## 6. 故障排查

### 6.0 磁盘：先看清楚再动手

（磁盘占用与清理见上一节；本节讲两个相关但独立的话题。）

### 6.0.1 管理员自己改密码

登录控制台后，**"我的账号"里有修改密码的入口**（不需要 SSH 到服务器）：

1. 填当前密码、新密码（至少 12 位）、再输一次；
2. 提交后**其它已登录的管理员会话立即失效**，**当前这个会话保持登录**（服务端会重新下发 cookie）；
3. 忘了当前密码就只能到部署机上执行 `bin/mt.sh admin-passwd`。

命令行与网页改的是**同一个文件**（`state/admin.json`），两边互通：谁最后改的，就以谁的为准。

### 6.0.2 让所有管理员重新登录

```bash
bin/mt.sh admin-kick          # 只吊销会话，密码不变
bin/mt.sh admin-passwd        # 改密码（同样会吊销已登录的会话）
```

机制：控制台会话是"过期时间 + 用 `state/admin.key` 签的 HMAC"，**换掉密钥就等于全部吊销**。
网关每次请求都重新读这个文件（不缓存），所以**不需要重启**——这也是这个功能的意义所在：想吊销
的场合通常等不了重启。

`admin-passwd` 默认同时轮换密钥（改密码多半正是因为怀疑泄露，留着旧会话等于没改）；要保留会话
加 `--keep-sessions`。

**实测**：登录后执行 `admin-kick`，同一个 cookie 访问状态接口立刻从 200 变 **401**，密码不变、
可重新登录；改密码同理。租户侧不受影响。

**注意**：`state/admin.key` 与备用控制面共用，轮换会连备用的会话一起吊销（这是有意的：一个权威）。

### 6.0.3 磁盘 I/O 限额：**目前不生效，别当成已启用**

`bin/render.js` 支持给租户容器配块设备吞吐上限（`MT_TENANT_DISK_WRITE_BPS` / `MT_TENANT_DISK_READ_BPS`，
格式 `<设备>:<速率>`，也支持按租户写进 `tenants.json` 的 `limits.diskWriteBps`），**但默认关闭，
而且在现网这台机器上实测无效**：

| 项 | 实测 |
|---|---|
| Docker 记录配置 | ✓ `BlkioDeviceWriteBps=[/dev/mapper/centos-home:52428800]` |
| 容器 cgroup 实际值 | ✓ `253:2 52428800`（设备号正确） |
| 容器内写 200MB | ✗ 限速后 **908 MB/s**，不限速 800 MB/s——**没有任何限制** |

原因：cgroup v1 的块设备限速只在**回写**时生效，而回写发生在 flusher/kworker 的 cgroup 里，
不是容器自己的。内核本身支持（`CONFIG_BLK_DEV_THROTTLING=y`、cgroup 接口文件都在），是这套
cgroup v1 + 3.10 的组合拦不住容器的缓存写。

**相对权重也不要指望**：`blkio.weight` 是 CFQ 的公平性设置，而本机调度器是 `deadline`，
配了等于没配。

所以磁盘争抢目前**没有**技术手段挡住。可行的替代方向（都需要额外的结构性改动，未实施）：
给每个租户独立卷/文件系统并在其上做配额；或换成 cgroup v2 的环境；或在存储层（LVM thin /
外部存储）限速。

**另一条要留意的坑**：`docker run --device-write-bps` 会被 Docker **静默忽略**
（`docker inspect` 里是空的），别用它做验证；测试必须走 compose 生成的容器。

```bash
bin/mt.sh disk report
```

它按"压力在哪"分段报告，因为**这台机器的两个分区性质完全不同**：

| 位置 | 现网 | 装什么 | 压力 |
|---|---|---|---|
| `/`（50G） | 78% 用满 | **Docker 镜像与容器** | 重建一次就多几层，是真正会满的地方 |
| `/home`（441G） | 5% | 租户数据、备份、部署目录 | 空间充裕，但会话会一直长 |

**回收镜像层**（现网实测一次回收过 1.7MB；机器上最多时曾有 50 个悬空镜像）：

```bash
bin/mt.sh disk prune-images          # 只报告，不动手
bin/mt.sh disk prune-images --yes    # 真的删
```

这是**全机范围**的操作（悬空镜像没有标签、也没有容器引用，删掉不影响任何运行中的栈，只影响
以后重建的缓存命中）。这台机器上还有 Harbor、Nexus、Nacos 等别的栈，所以需要显式 `--yes`；
脚本也**不会**用 `docker system prune`（那会连带清网络与构建缓存）。

**清理旧会话**：

```bash
bin/mt.sh disk prune-sessions --older-than 90 --dry-run     # 先看会删什么
bin/mt.sh disk prune-sessions --older-than 90 --archive     # 归档后再删
bin/mt.sh disk prune-sessions --older-than 90 --tenant alpha # 只处理一个租户
```

> `--older-than N` 的含义是**超过 N 个完整的 24 小时**（`find -mtime` 的语义）。
> `--older-than 0` 表示"超过一天"，**不是**"全部"——这点很容易误解。

加了 `--archive` 会先打包到 `backups/sessions-<租户>-<时间戳>.tar.gz` 再删；打包失败就跳过该
租户，不会出现"没归档却删了"的情况。会话是用户的对话记录，删掉不可恢复，所以默认**不归档不删**
（不加 `--archive` 也能删，但要你自己确认）。

**实测**：对一个租户删了 15 个超 24 小时的会话——先归档（174K，含 15 个会话目录，可恢复），删除后
该租户工作区正常、冒烟 15/15、doctor 0 失败，其它三个租户的会话数未变。

按症状查。先分清两个最常混淆的状态码：

| 页面/状态码 | 含义 | 先去查 |
|---|---|---|
| **502** | 运行时**已注册但连不上** | 容器是否在跑（`docker ps`）、地址是否变过 |
| **503 +「还没有注册运行时」** | 控制面**不认识**这个租户的运行时 | `bin/mt.sh runtimes`，然后 `bin/mt.sh register <租户>` |
| **503 +「启动 token 可能已过期」** | 注册过，但 token 是上一次启动的 | `bin/mt.sh register <租户>` |

### 登录后看到「租户运行时还没有注册」

**原因**：容器没起，或者控制面还没收到该运行时的注册。

```bash
docker ps -a --filter name=mt-dsh-<租户>    # 容器在不在、跑没跑
bin/mt.sh runtimes                          # 控制面认识它吗
bin/mt.sh register <租户>                    # 手动补一次注册
```

### 刷新后看到「启动 token 可能已过期」

**原因**：容器重启过，DSH 换了新的启动 token，而控制面手里还是旧的。这通常发生在
你手工 `docker restart` 而没有走 `bin/mt.sh restart` 之后。

```bash
bin/mt.sh register <租户>
```

### 界面能打开，但点什么都没反应

**原因（已修复，仅作历史参考）**：网关改写 Host 时没有同步改写 Origin，DSH 的防护网
会因此拒绝所有 `/api/*`。如果你的部署是 2026-10-01 之前的版本，先升级网关。

**自查方法**：浏览器 F12 → Network → 过滤 `api`，正常应是 200；如果是 403 `forbidden`，
就是这个问题。同时看 WS 连接是不是 101。

### 租户说模型报错

```bash
bin/mt.sh usage                     # 先看有没有被拒绝的调用
docker logs mt-model-gateway --tail 50
docker logs mt-egress-proxy --tail 50   # 出网是否被拦
bin/model-check.sh --tenant <租户> --user <用户> --password <密码>   # 端到端真实调用
```

### 租户能访问宿主上的其它服务

**已修复（2026-10-02 起）**：网桥名不再由 Docker 随机生成。渲染时通过
`com.docker.network.bridge.name` 固定为 `mtdocker0`，`isolate.sh` 与 `doctor` 都按这个名字
解析，所以**重建网络后规则依然有效，不需要重跑**。

实测：重建网络前后网桥都是 `mtdocker0`，规则不动，隔离照旧（宿主端口被丢弃、出口代理与模型
网关可连）。

如果你在旧版本上遇到这个问题（那时规则绑定 `br-xxxx`）：

```bash
bin/mt.sh isolate status
bin/mt.sh isolate apply      # 重新绑定到当前网桥
bin/mt.sh doctor             # 确认「实测」那一项通过
```

隔离规则写在 firewalld 里，但**网桥本身不在了规则就无处可施**——`apply` 会把旧网桥的规则
换成当前网桥的。更换网桥名（改 `.env` 里的 `MT_BRIDGE_NAME`）之后也要重跑一次。

### 磁盘快满

`/` 只有 50G，`/home` 有 400G+，部署在 `/home/dsh-mt`。日志已限制上限
（每容器 10m × 3 个文件），但 `logs/access.jsonl` 与 `logs/model-usage.jsonl` 是自己写的，
**目前不会自动轮转**：

```bash
du -sh /home/dsh-mt/logs /home/dsh-mt/tenants/*/home   # 谁占地方
```

租户会话日志会随使用增长，这是正常的；不要动 `tenants/*/home/sessions/` 里的内容。

## 7. 现在**做不到**的（已知缺口）

这些不是配置问题，是当前实现里确实没有的能力。按影响排序：

| 缺口 | 影响 | 变通做法 |
|---|---|---|
| ~~租户之间无二层隔离~~ | **已解决**：每个租户独立网桥，实测两两互不可达 | 见下方说明 |
| 没有登录防爆破 | 弱密码可被在线暴力尝试 | 用强密码；必要时 `firewalld` 限制来源 IP |
| 改密码不吊销已登录会话 | 密码泄露后无法立刻踢人 | `bin/mt.sh restart <租户>` 强制中断 |
| 没有按租户配额/限流 | 单个租户可占满模型额度 | 靠 `bin/mt.sh usage` 事后发现 |
| 租户不能自助改密码 | 每次改密都要找你 | 接受，或后续做自助页 |
| 恢复是全有全无 | 不能只恢复某一个租户 | `restore --data-only` 折中 |
| 管理员操作没有审计 | 谁改了什么查不到 | 会话记录里能看到租户侧行为 |
| 没有 Web 控制台 | 管理必须 SSH | 本手册即操作面 |

### 租户之间的隔离（已解决）

**现在每个租户各有自己的网桥**，实测两两互不可达。开启方式写在 `.env`：

```bash
MT_TENANT_NETWORKS=all        # 全部租户各自隔离；也可写 delta,gamma 只隔离其中几个
MT_TENANT_NETWORKS=           # 留空 = 都放在主网桥上（默认）
```

改完执行 `bin/mt.sh up`，再执行一次 `bin/mt.sh isolate apply`（新网桥要各自配上宿主端口规则）。

**它怎么工作的**：每个租户在 `mt-net-<租户>` 上，网段取自租户 id 的哈希（所以增删租户不会让其它
租户重新编号），网桥名固定为 `mtbr<hash>`。模型网关接入**所有**租户网络——它是租户唯一还需要
跨网访问的服务；出口代理地址按租户计算，因为每个网桥有自己的网关 IP。

**为什么不是 iptables/ebtables**：同网桥容器之间是二层转发，本机 `bridge-nf-call-iptables=0`
所以不过 iptables；改那个 sysctl 会影响宿主上所有网桥。ebtables 试过，丢弃规则生效但模型网关的
放行例外在这套内核上匹配不上（包计数器始终为 0），装上就会切断模型链路，因此改用独立网桥。

**代价**：每个租户多一个网桥（显式分配网段，因为默认地址池已被其它系统耗尽）；新增租户后要跑一次
`isolate apply`。`doctor` 会检查每个网桥是否都有规则。

我实现并实测过用 **ebtables** 在同网桥内隔离租户，**结论是放弃**，原因如下，留着供以后参考：

- 同网桥容器之间的流量是二层转发，**不经 iptables**（本机 `net.bridge.bridge-nf-call-iptables=0`）。
  改这个 sysctl 会影响宿主上**所有**网桥（Harbor、Nexus、Nacos 等），不能动。
- ebtables 是网桥层的原生过滤，不受该开关影响，所以先试了它。丢弃规则**确实生效**
  （实测租户之间连接超时）。
- 但**模型网关的放行例外匹配不上**：`-p IPv4 --ip-proto tcp --ip-dport 8080 -j ACCEPT` 这条规则
  包计数器始终为 0，而丢弃规则计数上千。结果是租户连不上模型网关，冒烟与验收同时失败。
  （`ebt_ip` 模块加载了、规则顺序也没问题。）
- **不隔离只是缺少一层防护；装上一个切断模型链路的隔离是故障**，所以回滚了，没有留在部署里。

要真正做成，可行路径是**每个租户一个独立网桥**（L2 天然隔离），代价是模型网关要接入所有租户网络、
出口代理由每网桥的网关 IP 决定（`MT_EGRESS_PROXY` 需按租户给值），而且要为每个网桥显式分配网段
——本机 Docker 默认地址池已被其它系统耗尽。这是结构性改动，需要单独排期。

**核心假设已实测验证**（用一次性探针网络，验证后完全拆除，现有部署不受影响）：

| 假设 | 实测结果 |
|---|---|
| 接入多个网络的容器，在每个网络里都能按名字解析到 | 模型网关接入探针网络后，探针容器解析它得到该网络上的地址 `10.98.0.2`，**可连** ✓ |
| 只接入网络 A 的容器访问不到只在网络 B 上的容器 | 探针容器访问 mt-net 上的租户 → **超时/不可达**，且 DNS 解析失败（`EAI_AGAIN`）✓ |
| 容器能经自己网桥的网关 IP 访问宿主出口代理 | 经 `10.98.0.1:3128` **可连** ✓ |

**实施方案**（尚未动手，按此顺序可保证每步留下的都是可用状态）：

1. 先做**单租户试点**（挑一个租户迁到 `mt-net-<租户>`），其余三个留在 mt-net，验证"试点租户正常
   工作、且与其余租户互不可达"；
2. `bin/render.js`：每租户一个网络 + 显式网段（按租户 id 哈希取第三段，冲突时顺延，避免增删租户
   导致其它租户重新编号）+ 每租户的 `MT_EGRESS_PROXY` + 模型网关接入所有租户网络；
3. `bin/isolate.sh`：对**每个**租户网桥各应用一遍宿主端口规则（现在只处理一个网桥）；
4. `bin/node-agent`：发现逻辑要跨多个网络（现在只认一个 `MT_NETWORK`），否则迁走的租户不再被上报；
5. `bin/smoke.sh` / `accept.sh`：假模型容器也要接入被测租户的网络。

**风险点**：迁移会重建网络，租户容器要重建并重新注册；网段分配要显式（默认地址池已耗尽）。
