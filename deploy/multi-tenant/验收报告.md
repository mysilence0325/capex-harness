## 3. 部署过程中的两个真实缺陷（已修复）

### 3.1 局域网无法访问：宿主 `ip_forward = 0`

- **现象**：VM 内 `curl 127.0.0.1:8090` 与 `curl <部署主机>:8090` 都返回 200，但外部客户端连接 8090 超时。
- **根因**：宿主 `net.ipv4.ip_forward = 0`。外部包在 nat PREROUTING 被 DNAT 到 bridge 网段后需要转发，被内核静默丢弃；VM 自身访问走本地路径，因此掩盖了问题。同机其它 stack 的映射端口（Harbor 18083、Grafana 13000、Nacos 18081、capex 18000/8089）实测同样不可达，属宿主既有状态，非本部署引入。
- **修复**：控制面改用 `network_mode: host` 直接监听宿主端口；租户容器保持在 `mt-net`、不发布端口，网关经 Docker API 解析其地址。**未修改宿主任何全局设置**（开启 `ip_forward` 会同时暴露其它服务的端口，属全机变更，留给运维决定）。

## 4. 管理员如何给租户提供模型（当前唯一待办）

局域网内由管理员统一配置私有化模型，租户在界面里自选：

```bash
cd /opt/dsh-mt
vi model.patch.yml     # 填 baseURL、模型 id（替换全部 CHANGE-ME），可列多个模型供租户选
vi model.env           # 填 GATEWAY_API_KEY=<真实 key>
bin/mt.sh model        # 渲染 → 应用到全部租户 → 重启 → 等待就绪
```

- `model.patch.yml` 的内容写进每个租户 profile patch 的标记块；块外是租户自己的设置，重新渲染不覆盖。
- 租户在 Web UI 的模型选择器里看到管理员提供的模型并按会话选择；默认模型由管理员在 `providers` 里排第一的模型决定。
- 需要按租户隔离计费时改用每租户 key：`bin/mt.sh key <租户> <key>` 后 `bin/mt.sh up`。
- 文件里只要还有 `CHANGE-ME`，渲染就跳过它，租户只看到内置的官方 DeepSeek 卡片。

## 5. 运行与运维

| 命令 | 作用 |
|---|---|
| `bin/mt.sh up` | 渲染 + 构建网关 + 启动/重建 + 等待全部租户就绪 + 打印入口 |
| `bin/mt.sh status` / `ps` | 容器状态与各租户就绪情况 |
| `bin/mt.sh logs <租户>` | 查看某个租户运行日志 |
| `bin/mt.sh add <id> --user <u> --title <t> --edge-port <p>` | 新增租户（自动分配端口、生成密码） |
| `bin/mt.sh passwd <id> <user>` | 重置密码 |
| `bin/mt.sh remove <id>` | 从注册表移除（数据目录保留） |
| `bin/mt.sh model` | 应用模型配置并重启全部租户 |
| `bin/mt.sh smoke` / `accept` | 隔离回归 / 端到端验收 |
| `bin/mt.sh down` | 停止整套（数据保留在磁盘） |

数据与备份：

- 每个租户的数据全在 `tenants/<租户>/{home,workspace}`；**备份 `home` 就等于备份该租户的全部会话、设置与凭据**。
- 网关会话密钥在 `state/session.key`（删除＝所有人重新登录）。
- 审计在 `logs/access.jsonl`（租户、用户、方法、URL、状态码、耗时）。

资源占用（实测）：网关约 28 MB，每个租户运行时约 95–100 MB，空闲 CPU 占比 < 0.5%；宿主剩余内存约 4.4 GB、磁盘 12 GB。

## 6. 安全边界（部署方必须知道的取舍）

1. **容器即隔离边界**。宿主内核 3.10、未启用 user namespace，DSH 自带的文件沙箱（bwrap/Landlock）不可用，因此租户运行时以 `DSH_PERMISSION_MODE=danger-full-access` 启动（同时把审批策略设为 `never`，避免无人值守时挂起）。租户的 agent 在其容器内拥有完全权限，这是形态 C 的既定设计。
2. **网关是唯一信任边界**。它读取 Docker socket 以获得各租户当前的启动 token；宿主 root 与网关容器等价。租户容器不挂载该 socket，也不发布任何宿主端口。
3. **租户之间的分隔手段**：独立容器与命名空间、独立 `DSH_HOME`、独立凭据与随机签名密钥、互相不认的 DSH cookie（cookie 名由各租户的内部 authority 派生）、网关层按会话固定租户并拒绝跨租户地址。
4. **当前没有 TLS**：内网明文 HTTP，网关 cookie 未加 `Secure`。需要 HTTPS 时在网关前再加一层 TLS 终结。
5. **配额是容器级的**：内存/CPU/PID 已限制；磁盘配额需要宿主 project quota 或独立卷。
6. **没有租户自助开通**：新增租户由运维执行 `bin/mt.sh add`。

## 7. 与既有部署的关系

`/opt/dsh-mt` 是独立的一套 compose 项目（网络 `mt-net`，容器名前缀 `mt-`），与宿主上原有的单租户部署 `/opt/dsh-vm`、`/opt/dsh-offline`（容器 `dsh-web`、`dsh-lan`，端口 3080）以及 Harbor、capex、aero-quality 等系统完全并存、互不影响，未改动其中任何一个。

构建注意：本机 Docker Hub 不可达，网关镜像用经典构建器（`DOCKER_BUILDKIT=0`）构建，`bin/mt.sh` 已内置该处理。

## 8. 运行时换成本地源码构建

原先三个租户跑的是 npm 公开发行版 `dsh-web:0.2.0-rc.2`——本地源码的改动（浏览器下限 chrome90 等）**从未进入部署**。现已换成本地构建。

做法：把本地构建产物按容器内安装路径组织成覆盖层，叠到 npm 基础镜像上（`image/Dockerfile` 一条 COPY）。
原生插件与依赖解析全部保持不变，镜像只增加约 65 MB。

**证据**

| 检查 | 结果 |
|---|---|
| 三个租户的镜像 | 均为 `dsh-web:local-20261001T0212` |
| 容器内 `dsh-web-frontend/dist/index.html` 哈希 | `0ebe24dc…`，与本地构建**逐字节一致**（三个租户皆是） |
| 服务端返回的 index.html 引用的入口脚本 | `assets/index-D6f0Sbyx.js`，与本地构建完全一致 |
| 该入口脚本经网关下载 | HTTP 200 |
| 租户数据 | 重建容器后会话数、凭据文件全部保留 |
| 隔离冒烟 / 端到端验收 | 15/15、11/11（含一次真实模型调用落盘） |

`publish-image.sh` 把"镜像内 index.html 哈希 = 覆盖层哈希"做成构建后的强制校验——
第一次构建就是因为 COPY 目标多了一层 `node_modules` 而被它拦下的。

刻意排除：`build:native-system` 产出的是构建机的 `.node`（不能跨平台塞进 Linux 容器）、Electron 桌面包。

1. 干净状态备份 → 归档不含任何污染物；
2. 制造破坏：投放 `POLLUTION.txt`，删除 beta 的一个会话目录；

## 10. 模型接入

管理员配置、租户自选。凭据放在 `model.env`（`env_file` 注入每个租户容器，0600、不进版本库），
DSH 内置的 `deepseek-official` 卡片指向 `https://api.deepseek.com`，租户界面里直接出现两个模型：

| 模型 id | 显示名 |
|---|---|
| `deepseek-flash` | DeepSeek-V41-Flash |
| `deepseek-v4-pro` | DeepSeek-V4-Pro |

**实测**（`bin/model-check.sh`，走真实 API，不是假模型）：alpha 与 delta 两个租户各完成一次真实对话，
回复分别落在各自租户的会话日志里；测试固定选 `deepseek-flash` 并核对回复确实来自该模型，
不依赖会话默认值，也不会把测试打到更贵的 `deepseek-v4-pro` 上。

### 途中发现的硬阻塞：租户没有外网出口

第一次真实调用直接失败（`TRANSPORT`）。根因不是模型配置，而是**宿主 `net.ipv4.ip_forward=0`**：
bridge 容器因此没有任何外网路由——实测容器内 DNS 解析失败（`EAI_AGAIN`）、连裸 IP 也超时，
而宿主自己访问同一端点是正常的。

两条路：

| 方案 | 代价 |
|---|---|
| 打开 `ip_forward` | 一行 sysctl，但会让宿主上 **其它系统的已发布端口一并暴露给局域网**（Harbor、Nexus、Grafana、Nacos、capex 等，实测此前从局域网均不可达） |
| 受控出口代理 | 多一个容器，但只放行租户，且顺带成为租户的出网边界 |

选了后者：`mt-egress-proxy` 跑在宿主网络命名空间（用宿主的出口），监听 3128——
**该端口没有在防火墙放行**，所以只有容器连得上，局域网连不上。实测：

```
容器 -> 宿主:3128                       HTTP 200（可达）
容器经代理 CONNECT api.deepseek.com:443  HTTP/1.1 200 Connection Established
容器经代理 CONNECT <出口代理宿主地址>     HTTP/1.1 403 Forbidden   （私网地址被拒）
容器经代理 CONNECT 127.0.0.1:22          HTTP/1.1 403 Forbidden   （回环被拒）
```

租户容器的 `HTTPS_PROXY`/`HTTP_PROXY` 由 `bin/mt.sh up` 自动探测网关地址并写入 `.env`。
`doctor` 每次都会从租户容器实测一遍上述三项。

顺带修掉一个真实缺陷：compose 里 `DEEPSEEK_API_KEY: ${MT_<租户>_DEEPSEEK_API_KEY:-}` 这种写法，
空默认值会**覆盖** `env_file` 注入的共享凭据——共享 key 根本传不进容器。现在只在租户确有独立值时
才生成该行。

## 11. 传输加密

`bin/mt.sh cert` 生成证书，`bin/mt.sh up` 让公开端口切到 HTTPS。实测：

| 检查 | 结果 |
|---|---|
| `https://<主机IP>:8090/`（带证书校验） | 200，`ssl_verify_result=0` |
| `https://alpha.dsh.local:8091/`（SAN 覆盖主机名） | 200 |
| 明文 `http://<主机IP>:8090/` | 被拒 |
| `dsh-auth-*` cookie 在 HTTPS 下 | 补上 `Secure` |
| 同一 cookie 在明文运维端口下 | 不带 `Secure`（否则浏览器不会回传） |
| 本机运维脚本 | 走 loopback 明文 8099，全部通过 |

两个实现要点：

1. **两级链而非单张自签证书**。客户端要导入签发者，而宿主 curl 用 NSS，它拒绝把 `CA:TRUE`
   的证书当服务器证书（`Certificate type not approved for application`）；反过来单张
   `CA:FALSE` 的自签证书在 OpenSSL 下又报 `Issuer certificate is invalid`。
   现在是自签 CA + 由它签发的服务端证书，两边都通过。
2. **`Secure` 由网关补**。DSH 不知道自己在 TLS 终结之后，它的 cookie 属性由它自己决定；
   网关按请求是否走 TLS 决定是否追加 `Secure`，明文运维端口上不加。
