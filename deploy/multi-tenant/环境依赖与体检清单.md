# 环境依赖与体检清单

记录两件事：**什么都不装就能做的环境体检怎么做**，以及**部署前需要在宿主上准备什么**。两者不要混：体检脚本已经改成只用 `python3`（Ubuntu 自带），局域网装不了任何东西也能出结论。

## 一、现在就能做：零安装环境体检

```bash
# 1) 宿主能力（末尾带上模型端点 URL，顺便测那台机器能不能连到它）
scp bin/preflight.sh <目标机>:/tmp/
ssh <目标机> 'bash /tmp/preflight.sh http://15.11.40.44:3100 | tee /tmp/dsh-env-1.txt'

# 2) 端点能力（协议、模型 id、流式、函数调用）
scp bin/model-probe.sh <目标机>:/tmp/
ssh <目标机> 'bash /tmp/model-probe.sh http://15.11.40.44:3100 <key> | tee /tmp/dsh-env-2.txt'
```

两个脚本都只用 `python3`：`model-probe.sh` 的 HTTP 调用全部由内嵌的 python 完成（不需要 curl），`preflight.sh` 读 `/proc/meminfo`（不需要 procps），并能直接向内核查询 Landlock ABI（不需要任何镜像）。在没装 curl / procps / bubblewrap / firewalld / xfsprogs 的机器上都能出结论。

**判读表**

| 看到 | 结论 |
|---|---|
| `内核直接报告 Landlock ABI 1（syscall 实测）` | 沙箱可用（Landlock 自 5.13 起；ABI 5 = 内核 6.10+ 才算 full） |
| `bwrap 未实测` | 不影响结论：bwrap 是"覆盖更宽"的可选项，不是前提 |
| `cgroup v1` | 内存/CPU/PID 可用，磁盘 I/O 限速无效 → 磁盘靠配额 |
| `宿主能连上模型端点` | 试点可以落在这台机器上；不通就必须先解决网络 |
| 端点三项（普通对话 / 流式 SSE / `tools` 函数调用） | 任一 ✗ → 这个端点不能直接接 DSH |

## 二、部署前需要准备的依赖

| 依赖 | 用途 | 不装的后果 | 必需 |
|---|---|---|---|
| **docker-ce + compose v2** | 一切：控制面、租户运行时、脚本容器 | 跑不起来 | 是 |
| **python3 >= 3.6** | doctor / acceptance / alert-sink 与两个体检脚本 | 检查类脚本失败 | 是（Ubuntu 自带） |
| `curl` | `doctor`、`acceptance` 的 HTTP 检查（Prometheus 抓取、端点探测、控制台登录） | 那些检查报错 | 部署阶段需要，也可改成走容器执行 |
| ~~`firewalld`~~ | **不需要了**：`bin/isolate.sh` 有 iptables 后端（见第三节） | — | 否 |
| `xfsprogs` | `quota.sh` 用 `xfs_quota` 设每租户磁盘配额 | 磁盘配额无法强制（不影响能不能跑） | 需要配额时 |
| `bubblewrap` | 沙箱链首选（bwrap → Landlock），覆盖比 Landlock 宽 | 退到 Landlock（可用，但只治理部分访问类别） | 否，可选；要它就跟 `curl` 一起打进**镜像** |
| `iproute2`（`tc`/`ss`）、`util-linux`（`nsenter`） | 租户网络限速、监听检查 | 限速不可用 | Ubuntu 自带 |
| `openssl` | `make-cert.sh` 生成本地证书 | 用你们 CA 签发的证书即可替代 | Ubuntu 自带 |

`bubblewrap` 要装在**租户镜像里**（容器内）才起作用：宿主装了、容器里没有，DSH 仍然只能用 Landlock。它和 `curl` 都在基础镜像构建层加，**不要在 overlay 那层装**——那层只叠代码，会让每次构建都要网络。已在部署机上实测这条改法可行（构建出的镜像里 `curl 7.88.1` 与 `bubblewrap 0.8.0` 都在）：

```dockerfile
FROM <你们的基础镜像>
RUN apt-get update -qq \
 && apt-get install -y -qq --no-install-recommends curl bubblewrap \
 && rm -rf /var/lib/apt/lists/*
```

`curl` 进镜像的另一个用途：宿主机没有 curl 时，`doctor` / `acceptance` 会用 `bin/lib-http.sh` 把 curl 跑在这个镜像里（详见第三节）。

## 三、不是包、但要在宿主上决定的

| 项 | 说明 |
|---|---|
| cgroup v1 → v2 | Ubuntu 20.04 可在 GRUB 加 `systemd.unified_cgroup_hierarchy=1` 并重启；之后块设备限速才生效 |
| 数据盘配额 | XFS + `prjquota` 挂载参数（改 `fstab`，重启生效）；根分区是 ext 家族时 `quota.sh` 不适用 |
| 租户到宿主的端口隔离 | **不再需要 firewalld**：`bin/isolate.sh` 自动选后端（有 firewalld 用它，没有就用 iptables 专用链）。iptables 规则重启会丢，所以用 `bin/isolate.sh install-boot` 装一个 systemd 单元开机重建；`ufw` 启用时它重写 INPUT 可能冲掉跳转，`status` 会提示。实测（CentOS 3.10 上强制 iptables 后端）：撤掉 firewalld 后租户可访问宿主端口 → 切到 iptables 后端后被拒 → 撤销后恢复 → 切回 firewalld 仍被拒 |
| 宿主没有 curl 时的检查 | `bin/lib-http.sh` 让 `doctor` / `acceptance` / `smoke` 等把 curl 跑进运行时镜像（`--network host` + 挂载 `/tmp` 与项目目录）。实测把宿主 `/usr/bin/curl` 移走后跑完整验收：85 项通过 / 0 失败 / 1 跳过 |
| 宿主 `ip_forward` 与 `bridge-nf-call-iptables` | 影响"租户能否访问宿主端口"与"其它系统的端口是否对局域网可达"，属宿主全局决策 |
| 离线镜像 | 首次部署需要 `docker save` / `docker load` 搬运基础镜像与 DSH 运行时镜像（是文件搬运，不是安装） |

## 四、体检结论（目标机 lenovo-02，Ubuntu 20.04.6 / 内核 5.15，2026-10-10 实测）

**结论：这台机器 + 这个端点可以支撑 DSH，环境测试通过（21 项通过 / 11 项警告 / 0 项不可用）。**

| 项 | 实测 |
|---|---|
| 内核 + LSM | 5.15，`lsm` 含 landlock；**内核直接报告 Landlock ABI 1（syscall 实测）** |
| 非特权 userns | 允许（`kernel.unprivileged_userns_clone=1`） |
| bubblewrap | **宿主上 bwrap 可用**（宿主级实测；容器里还要装了才生效） |
| cgroup | v1 → 磁盘 I/O 限速无效（内存/CPU/PID 可用） |
| Docker | 25.0.0 + compose v2 + overlay2 |
| 资源 | 112 核 / 431 799 MB 可用内存 / 根分区 439G 已用 85% |
| 模型端点 | **✓ 宿主能连上 `http://15.11.40.44:3100`** |
| 公网镜像 | 拉不到 → 离线导入 |
| 权限模式 | **`workspace-write` + 审批 `ask`**（bwrap 与 Landlock 两条路都在） |

端点实测（`bin/model-probe.sh`）：

| 检查 | 结果 |
|---|---|
| `POST /v1/chat/completions` | 400 "Invalid model name" → 路径存在，OpenAI 兼容 |
| `POST /v1/messages` | 400 同类错误 → 这个网关**同时**支持 Anthropic 风格（本部署走前者） |
| `GET /v1/models` | 200，可用模型：`deepseek-v4-flash`、`DeepSeek Flash`、`GLM 5.3 Flash`、`bge-m3`、`bge-m3:latest`、`bge-m3:ollama`、`bge-reranker-v2-m3` |
| 普通对话 | ✓ |
| **流式（SSE）** | ✓ |
| **函数调用（tools）** | ✓ —— DSH 的 agent 循环能跑 |

后三个 `bge-*` 是向量化/重排模型，**不要**放进租户的模型目录。

## 五、接入定稿（部署时直接照抄）

`model.patch.yml`：

```yaml
- id: llm-pi-ai
  config:
    providers:
      internal:
        displayName: 内网模型服务
        api: openai-completions
        baseURL: http://mt-model-gateway:8080/v1     # 指向网关，不是内网端点
        apiKeyEnv: DEEPSEEK_API_KEY                  # 租户的占位 key，由 render 注入
        models:
          - id: deepseek-v4-flash                    # 探针自动挑中的那个（默认模型）
            name: DeepSeek Flash
            contextWindow: 131072                    # 128k；不写会按 262144 算
            maxTokens: 8192                          # 输出上限，按端点能力调整
          - id: GLM 5.3 Flash                        # 注意：这个 id 里带空格，要逐字写
            name: GLM 5.3 Flash
            contextWindow: 131072
            maxTokens: 8192
- id: llm-deepseek
  disabled: true                                     # 隐藏内置卡片（Anthropic 路径 + 指公网）
```

`.env`（真凭据只进这里，绝不进 `model.env` 或租户容器）：

```
MT_UPSTREAM_BASE=http://15.11.40.44:3100
MT_UPSTREAM_API_KEY=<真 key>
```

应用与验证：`bin/mt.sh up`（`model.patch.yml` 的改动会写进各租户 patch 并重启租户；`.env` 改了要重建模型网关）→ `bin/model-check.sh --tenant <租户> --user <用户> --password <口令>` 做一次真实调用。

部署时还要在 `.env` 里定下的几项（都按这台机器的体检结论给值）：

```
DSH_PERMISSION_MODE=workspace-write   # bwrap 可用 + Landlock ABI 1 ⇒ 不必 danger-full-access
MT_TENANT_NETWORKS=all                # 每租户独立网桥
MT_BIND_IP=0.0.0.0                    # 局域网访问；只本机就写 127.0.0.1
MT_EDGE_PORT=8090
# MT_REGISTRY_* 留空：这台机器拉不到公网镜像，升级走 docker save / docker load
```

隔离规则（部署后各跑一次，重启后由 systemd 单元自动重建）：

```bash
bin/isolate.sh apply && bin/isolate.sh install-boot
```

## 六、重建运行时镜像与冒烟（两条脚本）

在源码检出上（Windows）：

```powershell
.\deploy\multi-tenant\build-image.ps1                 # 构建三个面 + 浏览器下限门禁 + 覆盖层 + tar.gz
.\deploy\multi-tenant\build-image.ps1 -SkipBuild      # 构建产物已在，只重打包
```

在部署机上：

```bash
bin/publish-and-verify.sh <覆盖层.tar.gz> --switch --mock
# 内网端点可达的机器上：
bin/publish-and-verify.sh <覆盖层.tar.gz> --switch \
  --smoke http://15.11.40.44:3100 <key> deepseek-v4-flash --expect 可用
```

两个实测踩过的坑，脚本里都已处理，换机器重做时要知道：

* **`bin/mt.sh up` 会重建容器 → 运行时的网络限速被清掉**。重放原先只写在"新增租户"里，切镜像这条路上没有，
  于是每次切换镜像限速都静默消失（`doctor` 的限速检查抓到过）。现在 `up` 在**等就绪之后**重放一次。
* **compose 的 `build` 默认走 BuildKit，会去 Docker Hub 解析基础镜像元数据**，在这类拉不到公网的机器上直接失败
  （实测 `docker-compose up --build` 死在 `failed to resolve source metadata`）。本部署一律 `DOCKER_BUILDKIT=0`，
  或干脆用本地镜像 `docker run` 起辅助容器（假模型、告警接收器都是这么起的）。

## 七、内网那台机器：镜像搬运与真实端点冒烟

本机与 VM 都到不了内网端点（15.11.40.44），所以"真实模型跑通 DSH"那一次在内网机器上执行：

```bash
# 有该镜像的机器上导出（载体镜像也一起带上，publish 以它为底）
docker save dsh-web:local-<时间戳> | gzip > dsh-web-local.tar.gz
docker save dsh-web:0.2.0-rc.2     | gzip > dsh-base.tar.gz

# 传到内网机器并导入
scp dsh-web-local.tar.gz dsh-base.tar.gz root@<内网机>:/tmp/
ssh root@<内网机> 'docker load -i /tmp/dsh-base.tar.gz && docker load -i /tmp/dsh-web-local.tar.gz'

# 拷冒烟脚本（含它依赖的 lib-http.sh）
scp deploy/multi-tenant/bin/dsh-smoke.sh deploy/multi-tenant/bin/lib-http.sh root@<内网机>:/root/

# 真实端点冒烟（默认 --network host：容器直接走宿主网络）
ssh root@<内网机> 'cd /root && bash dsh-smoke.sh dsh-web:local-<时间戳> http://15.11.40.44:3100 <key> deepseek-v4-flash --expect 可用'
```

判据：退出码 0、回答里出现 `--expect` 的文字、`$DSH_HOME/sessions` 下生成会话文件。之后按第五节部署。

## 八、部署前还差的三件事（都已知、都有方案）

1. **镜像**：目标机拉不到公网镜像 → 在有网机器 `docker save` 基础镜像（`node:22-bookworm-slim`）与 DSH 运行时镜像，`docker load` 过去。
2. **bubblewrap 进镜像**：宿主可用不等于容器可用 —— 在基础镜像构建层加 `apt-get install -y bubblewrap`。
3. **`curl` 与隔离规则**：`doctor`/`acceptance` 用到 `curl`（可改成走容器或 python3）；`isolate.sh` 用的是 firewalld，这台机器没有 → 改写成 nft/iptables（Docker 自带 iptables，已验证在）。
