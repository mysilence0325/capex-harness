# DSH 多租户私有化：落地评估

这份评估回答一个问题：**已经做出来的多租户能力，实际能不能用、哪里不能用**。结论全部来自部署机上的实测（2026-10-10，`192.168.122.137`），不是照着文档转述——文档里过时的地方在第五节单独列出。

总体判断：**架构与工具面完成度高，问题集中在"最后一公里"**。控制台页面的脚本自 2026-10-03 起就是坏的，浏览器里所有按钮都不响应，而接口、状态码、页面内容、`doctor`、`accept` 全都是好的；告警链路"通了"但每条记录都丢了告警名；增删租户会在网桥上留下撞车的 MAC，导致某个租户的模型调用静默全挂。这些问题的共同点是：**门禁存在，但门禁没有覆盖"人真正在用的那条路径"**。

本次一共修了 5 个 P0：控制台页面脚本（P0-1）、删租户误报失败（P0-2）、租户与模型网关 MAC 撞车（P0-3）、删租户残留 `.env` 键与孤儿网络（P0-4）、告警内容全丢（P0-5）。每条都附复现方式与验收标准。

## 三、缺陷清单

### P0-1 控制台页面脚本缺一个 `}`，整页按钮全部无效（已修）

- **现象**：管理员登录后表格停在"加载中…"，点"创建并开通""加用户"等任何按钮都没有反应；接口 `/__mt/admin/api/*` 全部正常。
- **根因**：`gateway/admin-page.js` 里 `loadHistory()` 的渲染体被整段删掉且没有补回收尾的 `}`（引入于 2026-10-03 改时间筛选那次），其后的 `const post = …` 及页面脚本其余部分全部被吞进函数体，服务端送出的脚本语法错误。仓库副本另有一处 `toggleSelect(''' + …)` 的引号转义错误（部署机那份是对的）。
- **证据**：用 TypeScript 解析器解析"服务端真正送出的脚本"——修复前 1–3 个语法错误（`'}' expected`、`';' expected`），修复后 0 个；`bin/doctor.sh` 新增的"控制台页面"检查也在部署机上通过了同一断言。
- **修复**：补回 `loadHistory()` 的渲染体与 `}`；修正 checkbox 引号转义；页内补上自己的 `escapeHtml`（原先调的是服务端那个同名函数，浏览器里不存在）；`removeTenant` 提示语里多转义的一层 `\\n` 一并改正。
- **验收**：登录控制台 → 表格有行 → 点"加用户"能真正发出请求（本次实测加用户成功、出现在状态里、删除后注册表复原）。

### P0-2 删除租户明明成功却报失败（已修）

- **现象**：在控制台删掉一个租户，接口返回 `{"ok":false,"error":"没有租户 xxx"}`，而实际上容器、数据目录、注册表条目都已经清干净了。
- **根因**：删除由节点代理执行，代理同时把注册表条目摘掉；控制面随后再读注册表时发现"没有这个租户"，把**已经成功的删除**报成失败。
- **发现方式**：按"管理员真正在用的那条路"做了一次完整往返——建租户、等就绪、再连数据删除。
- **修复**：控制面记住"代理已经删掉了"，此时注册表里不存在即视为成功（审计记 `registry-already-gone`）。
- **验收**：`bin/acceptance.sh` 新增的检查会真的建一个临时租户、等它就绪、再连数据删除，并核对注册表、容器、数据目录三处都回到原样。

### 说明：一次误判（已撤回）

用户反馈的"管理员界面新增用户加不了"，指的是控制台里的**新增租户**（表单上那个"首个用户名"字段），失败原因就是 P0-1 的页面脚本缺陷。我一开始把它理解成"给已有租户再加一个用户"，并据此实现了 `adduser`/`removeuser`；确认这个能力**不需要**之后已经全部撤掉（代码、门禁、文档一并回退）。现在这套部署维持一个租户一个账号：要再加一个互相隔离的空间，就新增一个租户。

**已确认的产品语义**：一个租户 = 一个账号 = 一个独占空间。`bin/mt.sh add <租户> --user <用户>` 一次同时创建两者；给同一个租户挂第二个账号会让两个账号共用同一个容器、同一份 home 与 workspace（也就是同一个空间），所以那不是"再加一个空间"的正确做法。`bin/doctor.sh` 现在会在某个租户的账号数不为 1 时点名（合成注册表验证过：`a(1)` 通过，`b(2)`、`c(0)` 被点名）。

### P0-3 一个租户与模型网关彻底不通，另外三个却正常（已修）

- **现象**：alpha 的模型调用全部失败，`docker exec mt-dsh-alpha` 里连 `mt-model-gateway:8080` 报 `EHOSTUNREACH`；beta/gamma/delta 完全正常。
- **根因**：`mt-dsh-alpha` 与模型网关在 `mt-net-alpha` 上**MAC 相同**（都是 `02:42:0a:62:8e:02`）。Docker 按容器在该网络上的 IP 生成 MAC（`02:42:` + IP）并在 IP 变化后**继续沿用它**；旧 MAC 留在网桥转发表里，两台容器在二层无法区分，ARP 与数据帧都会走错端口。这个 IP 是 `.2`、`mt-dsh-alpha` 是 `.3`，但 alpha 的 MAC 来自它更早的 `.2` 时期。
- **触发条件**：增删租户或重建容器。这次是被"新建租户→删除租户"的往返验证触发的——也就是说，管理员最常做的那两个动作就是它的触发条件。
- **修复**：`bin/render.js` 给每个租户容器**钉一个固定 MAC**（`tenantMac()`，由租户 id 哈希得到，前缀 `02:d5:`，避开 Docker 的自动生成前缀），不再随 IP 漂移。`doctor` 新增"租户网络"一节，逐网桥检查 MAC 重复。
- **验收**：4 个租户对模型网关的探测全部返回 401（未授权＝链路通）；`doctor` 报"租户网络上没有 MAC 冲突"。

### P0-4 删租户留下 `.env` 键与孤儿网络（已修）

- **现象**：删掉租户后，`.env` 里它的 `MT_<租户>_GATEWAY_API_KEY` / `_DEEPSEEK_API_KEY` 两行还在（`doctor` 报"已删租户的残留键"）；它的网络 `mt-net-<租户>` 也还在，而且因为模型网关接入了每一张租户网络，这张空网络会一直挂着网关端点。
- **根因**：`bin/mt.sh remove` 只做了"摘注册表 + 重渲染 + 删容器 + 删数据"，没有清理该租户的 `.env` 键与网络；重渲染只是不再引用它们，Docker 不会自己删。
- **修复**：删除时按 `render.js` 的命名规则（id 大写、短横线换下划线）清掉该租户的 `.env` 键；容器删掉之后断开网关端点并删除该租户的网络（顺序不能反：容器还在时网络删不掉）。
- **验收**：`bin/acceptance.sh` 的往返检查新增两条断言——该租户在 `.env` 里的键已清掉、该租户的网络已删除。

### P0-5 告警链路"通了但内容全丢"（已修）

- **现象**：`state/alerts/alerts.jsonl` 有 115 条记录，其中 114 条只有 `receivedAt` 与 `status`，没有告警名、租户、摘要——收到告警也不知道是什么。
- **根因**：`alerts/sink.js` 把 Alertmanager 的 webhook 载荷（`{status, alerts:[…]}`）当成**单条**告警解析，于是只有顶层 `status` 被读出来。自检之所以"通过"，是因为它只看落盘条数是否增加，而这个缺陷恰好不改变条数。
- **修复**：按 `payload.alerts[]` 逐条解析（仍兼容单对象与裸数组），保留 `groupKey`；`bin/alert-sink.sh test` 改为断言"新落盘记录里带着本次告警名"。
- **附带发现并修掉**：重建接收器会换 IP，而它与 Alertmanager 在 `capex-ai-lab_ops` 上**MAC 相同**（都是 `02:42:ac:19:00:02`），网桥分不清两台，Alertmanager 的邻居表项永远是 incomplete，报 `no route to host`。现在接收器钉固定 MAC，`up` 会探测投递能力并在必要时重启 Alertmanager，撞车时直接点明原因。
- **验收**：`bin/alert-sink.sh test` 落盘一条含 `name`/`severity`/`summary`/`groupKey` 的记录。

### P1-1 宿主全局设置与文档相互矛盾（已按当前状态改写文档）

宿主 `net.ipv4.ip_forward=1`、`net.bridge.bridge-nf-call-iptables=1`，而 README 与验收报告都写着"刻意没有改"。后果已实测：从部署机之外的客户端可以直连 `3080`（既有单租户 dsh-web）、`13000`（Grafana）、`18081`（Nacos）、`18082`（Nexus）、`19090`（Prometheus）、`19093`（Alertmanager）。

本次**没有回退它们**：把 `bridge-nf-call-iptables` 关掉会让租户→宿主的隔离规则（依赖 iptables INPUT）失效，属净损失；`ip_forward` 是宿主全局项，影响其它栈。改为：文档写明现状、`doctor` 报出事实，暴露面交给运维决定。

### P1-2 镜像分发链路当前不可用

Harbor 的 `nginx` / `registryctl` / `redis` 容器已退出、`harbor-jobservice` 反复重启，`18083` 与 `8080` 均不可达；`.env` 里也没有 `MT_REGISTRY_HOST`。因此 `bin/mt.sh registry-push` 现在**不可用**，离线升级只能走 `docker save` / `docker load`。修复 Harbor 属于另一套 stack 的操作，本次未动，但 `doctor` 现在会明确报出来。

### P1-3 残留物（已清理）

- 删除 5 个幽灵网络 `mt-net-delta2/3/4`、`mt-net-newone`、`mt-net-tr572`，并清掉指向已消失网桥的 10 条 `firewalld` 规则（规则条数 20 → 10，覆盖当前 5 条在用网桥）。
- 3 个 `restore-aside-*` 目录移入 `attic/`（可回退，不再堆在项目根）。
- 删除 `MANIFEST.txt` 与两份过期 `.env` 副本（含模型凭据的旧快照）。
- 悬空镜像 49 → 6。
- `.acceptance-credentials.json` **刻意保留**：验收脚本按设计从 `$PWD` 读它，它已被 `.gitignore` 排除、权限 0600、也不进备份。

### P1-4 已实现但没启用的能力（本次启用）

`state/quota.json` 与 `state/bandwidth.json` 原本都是 `{}`；alpha 没有模型限额。现在：4 个租户各 5 GB 磁盘配额意图、100 Mbit 双向限速、rpm=60。**注意**：配额能否真正拦截取决于 `/home` 是否以 `prjquota` 挂载，当前不能，需要改 `fstab` 并重启才生效（`bin/quota.sh set` 会打印这条说明）。

### P1-5 自检自身的不一致（已修）

`bin/doctor.sh` 只读环境变量、不读 `.env`，于是 `bin/mt.sh doctor`（mt.sh 已经 source 过 `.env`）与直接跑 `bash bin/doctor.sh` 会给出**不同结论**——同一份配置两种答案。现在脚本自己 source `.env`，两条路径都得到 67 通过 / 2 警告 / 0 失败。
