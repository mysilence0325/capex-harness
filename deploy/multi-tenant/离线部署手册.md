# DSH 多租户离线部署手册（目标机 15.11.70.37）

> 这份手册面向"拿到离线包、在一台没有公网的机器上把它跑起来"的人。
> 每一步都给出**命令**与**期望输出**；输出对不上就停下，按第 9 节对照表查。
> 深入原理与逐项重建见《从零重建手册.md》，Key 免口令登录见《Key免口令登录接入.md》。

## 0. 一分钟概览

目标形态：一台机器跑一个共享控制面 + 每租户一个隔离运行时；用户访问
`https://officeai.301.avic:496/ai/harness/`，装 Key 的免口令进自己的 DSH，
没装 Key 的用用户名口令登录。

```bash
# ① 校验并解开（整包约 645 MB，通常就是一个 .tar，不分卷）
sha256sum -c SHA256SUMS.bundle
# 只有当你收到的是 .tar.part00、.part01… 时才需要先合并：
#   cat dsh-offline-*.tar.part* > dsh-offline-<时间戳>.tar
tar xf dsh-offline-<时间戳>.tar

# ② 导入（在解开的包目录里）
cd dsh-offline-<时间戳>
./install-offline.sh --dest /data/dsh-mt      # 校验 + docker load + 铺开 + 生成 .env

# ③ 配置、建租户、启动、验证
cd /data/dsh-mt
vi .env                                        # 填 MT_UPSTREAM_API_KEY（一节 4）
cp tenants.csv.example tenants.csv && vi tenants.csv
bin/mt.sh add-batch tenants.csv --derive-id --credentials-file .tenant-credentials.json
bin/mt.sh cert
bin/mt.sh up
bin/mt.sh doctor
bin/acceptance.sh
```

## 1. 离线包：内容与校验

```
dsh-offline-<时间戳>/
├── 先读我.txt
├── MANIFEST.json      版本、git commit、三个镜像的 ref+id、目标站点参数
├── SHA256SUMS         包内全部文件的校验和（安装脚本会逐项核对）
├── install-offline.sh 目标机入口
├── images/            node:22-bookworm-slim / dsh-web:0.2.0-rc.2 / dsh-web:local-<时间戳>
├── overlay/           前端覆盖层（将来离线更新镜像用，见 8.2）
└── deploy/            部署代码与全部文档（干净副本：不含 .env、租户数据、日志）
    └── sandbox-debs/  一个 47 KB 的 bubblewrap 包：安装脚本把它打进运行时镜像的派生层
```

包外同级是一个整包 `dsh-offline-<时间戳>.tar`（**装得下就不分卷**；超过每卷上限时才切成
`…tar.part00`、`…tar.part01`）。`SHA256SUMS.bundle` 里是收到的那些传输文件的校验和——
无论一个还是几个，都是同一条命令。

**先校验，再解包**（这一条别省：内网搬运常见文件被截断）：

```bash
sha256sum -c SHA256SUMS.bundle     # 每一个传输文件都要 OK
cat dsh-offline-*.tar.part* > dsh-offline-<时间戳>.tar   # 没有 part* 就跳过这一行
tar xf dsh-offline-<时间戳>.tar
cd dsh-offline-<时间戳> && sha256sum -c SHA256SUMS   # 包内文件逐个校验
```

包**不含**：真模型密钥、租户名单、Docker/compose 安装包、DSH 源码检出。

> **在 Windows 上解开时注意**：系统自带的 `tar.exe` 对中文文件名支持不好，会**半途跳过**
> 中文命名的文档（《离线部署手册》《从零重建手册》等），解出来看着像"少了几份"，而退出码
> 只在最后一行提示。要用 Windows 解开就用 7-Zip，或者干脆在目标机（Linux）上解。
> 本次交付目录里已经附了一份**解开好的**包，供直接查阅与拷贝。

## 2. 目标机前置检查

这台机器的体检结论（2026-10-10 实测，见《环境依赖与体检清单.md》第 4 节）：
Ubuntu 20.04.6 / 内核 5.15（bwrap 与 Landlock 都可用）/ Docker 25 + compose v2 / 112 核。

部署前顺手确认四件事：

```bash
docker version --format '{{.Server.Version}}'      # 期望 2x.x
docker compose version || docker-compose version   # 期望有其一
df -h                                              # 选一块有余量的数据盘（见下）
date                                               # 时间偏差会让日志与 TLS 对不上
```

**选哪块盘**：`overlay2` 所在分区已用 86%、另有一块数据盘已 100% 满——**别把部署目录放在
overlay2 那块盘上**。挑一块余量充足的数据盘，部署目录就用它，例如 `/data1/dsh-mt`。
镜像解压后约 1.4 GB，租户每个 2 GB 内存限额 + 各自 workspace，备份还要占一份。

**端口**（宿主网络，都是控制面自己监听）：

| 端口 | 用途 | 对外 |
|---|---|---|
| 8090 | 统一入口（HTTPS） | 只给入口机 15.11.40.44 |
| 8091+ | 每租户专属入口 | 同上（可选） |
| 8099 | 运维明文端口 | 仅 loopback，脚本用 |
| 3128 | 租户出口代理 | 仅容器网络 |
| 3181+ | 租户运行时内部端口 | 仅容器网络 |

## 3. 导入与放置

```bash
cd dsh-offline-<时间戳>
./install-offline.sh --dest /data1/dsh-mt
```

它按顺序做四件事，任一步失败会停下并说清停在哪：

1. `sha256sum -c SHA256SUMS` 逐项校验；
2. 前置检查：docker/compose 可用、目标目录为空、磁盘余量（< 5 GB 会告警）；
3. `docker load` 三个镜像，并**逐个核对镜像 id 与 MANIFEST 一致**；
4. 把 `deploy/` 铺到 `--dest`，生成 `.env`（预填本手册的目标值，密钥留空）。

期望结尾输出：

```
装好了。接下来四步（手册《离线部署手册.md》第 4-6 节逐条对照）：
    1) 填密钥：  vi /data1/dsh-mt/.env
    ...
```

只想校验、不想改动任何东西时：`./install-offline.sh --check-only`（部署前门禁，退出码非 0 即有问题）。

## 4. 配置 `.env`（定稿逐项）

安装脚本已经写好下面这些值，**只需要填一行密钥**：

| 键 | 值 | 为什么 |
|---|---|---|
| `DSH_IMAGE` | `dsh-web:local-<时间戳>` | 本机构建的运行时镜像（含我们自己的前端） |
| `MT_BASE_PATH` | `/ai/harness` | 前置代理把它挂在 `/ai/harness/` 之下 |
| `MT_KEY_LOGIN_FROM` | `15.11.40.44` | 只接受入口机送来的 Key 身份 Cookie |
| `MT_UPSTREAM_BASE` | `http://15.11.40.44:3100` | 内网模型端点（OpenAI 兼容） |
| `MT_UPSTREAM_API_KEY` | **`<现场粘贴>`** | 真密钥不进包；**留空时模型网关拒绝启动**（设计如此） |
| `DSH_PERMISSION_MODE` | `workspace-write` | 沙箱**开着**：容器里走 Landlock（这台内核 5.15 = ABI 1，partial）。上机后跑 `bin/sandbox-check.sh` 确认；只有两条路都不可用时才改成 `danger-full-access`（容器即边界）并记原因 |
| `MT_SANDBOX_BWRAP` | 不设置（可选 `1`） | 强制走 bwrap（`--unshare-user`）。**只在 `bin/sandbox-check.sh` 报告它可用时才开**；开了之后 bwrap 起不来会直接报错，不会悄悄降级 |
| `MT_TENANT_NETWORKS` | `all` | 每租户独立网桥 |
| `MT_EDGE_PORT` / `MT_BIND_IP` | `8090` / `0.0.0.0` | 统一入口监听 |
| `TZ` | `Asia/Shanghai` | 日志与会话时间 |

```bash
cd /data1/dsh-mt
vi .env                    # 只改这一行：MT_UPSTREAM_API_KEY=sk-xxxx
grep -c '^MT_UPSTREAM_API_KEY=.\+' .env    # 期望 1（确认不是空的）
```

## 5. 建租户

手上只有**用户名和姓名**（Key 里的账号名 + 真名）就够了，租户 id 由工具推导：

```bash
cp tenants.csv.example tenants.csv
vi tenants.csv                                  # 替换成你们的名单，一行一个
bin/mt.sh add-batch tenants.csv --derive-id --credentials-file .tenant-credentials.json
```

期望输出（每个租户一行，id 由用户名推导）：

```
added 2 tenant(s)
  liuy-1	liuy_1	<随机口令>
  zhang01	zhang01	<随机口令>

==> 凭据已写入 .tenant-credentials.json（0600，含明文口令；不要放进备份或版本库）
```

规则与边界：

* 用户名里的下划线、点等非字母数字**一律并成一个连字符**（`liuy_1` → `liuy-1`）；数字开头补 `u-`；
* 推不出来的（中文用户名）会报错并要求那一行显式给 id，**整份清单一个都不建**；
* id 撞车自动换号（`liuy-1` → `liuy-1-2`）并打印换号；
* 租户 id 要能当主机名：小写字母开头、只含小写字母/数字/单个连字符、不能以连字符结尾；
* **用户名必须逐字等于 Key 里的账号名**，否则 Key 免口令登录认不出人（口令登录仍可用）。

只想登记不启动：加 `--no-start`，之后统一 `bin/mt.sh up`。

## 6. 启动与验证

```bash
bin/mt.sh cert          # 自签证书：公开端口切 HTTPS（cookie 的 Secure 靠它）
bin/mt.sh up            # 渲染 + 构建网关等镜像 + 起容器 + 注册运行时 + 等就绪
```

`up` 结束时会打印入口清单与限速恢复情况。接着逐条验证：

| 命令 | 期望 | 说明 |
|---|---|---|
| `bin/mt.sh doctor` | **0 项失败** | 通过数随租户数增加；两条固定警告（`model.patch.yml` 仍是模板、未配内网仓库）属正常。其中"沙箱"一节会对照"实际可用哪条"与 `DSH_PERMISSION_MODE`：配了 `workspace-write` 却没有沙箱会被报成失败（那种情况下租户的每条命令都会以 `SANDBOX_UNAVAILABLE` 失败） |
| `bin/acceptance.sh` | **全部通过** | 非 `--quick`；含控制台、MFA、隔离、Key 登录、子路径等 100 多项 |
| `bin/model-check.sh --tenant <租户> --user <用户名> --password '<口令>'` | 真实模型回答 | **这一条才证明模型链路通**（宿主能连端点 ≠ 容器能连） |
| `bin/dsh-smoke.sh <镜像> http://15.11.40.44:3100 <key> deepseek-v4-flash --expect 可用` | 退出码 0 | 真实端点冒烟，回答里出现"可用" |
| `bin/sandbox-check.sh` | 至少一条路可用 | **沙箱到底开没开**：分别探 bwrap 的原样参数、bwrap 加 `--unshare-user`、以及 Landlock 的功能性探针，并给出该用哪个 `DSH_PERMISSION_MODE` |

`bin/dsh-smoke.sh` 那一条同时验证了**沙箱链**：它会在租户里真的执行命令。若它以
`SANDBOX_UNAVAILABLE` 失败，说明容器里的 Landlock（ABI 1）这条路也没走通，把 `.env` 的
`DSH_PERMISSION_MODE` 改成 `danger-full-access`（容器本身即边界）再 `bin/mt.sh up`，
并把这个决定写进部署记录。`bin/sandbox-check.sh` 会把同一件事在几分钟内问清楚，优先用它。

浏览器再各看一眼（脚本判断不了观感）：带 Key 的机器打开入口应直接进自己的 DSH；
没有 Key 的机器应看到登录页且**两种方式都在**。

## 7. 接入前置代理与 Key 免口令

三件外部事（前两件已由你们验证过）：

1. **入口机 nginx**（15.11.40.44:6006）加一段：`/ai/harness/` → `https://15.11.70.37:8090`，
   保留前缀、`Host $http_host`（带端口）、转发 `Upgrade`、`proxy_buffering off`、超时放宽。
   完整片段见《README.md》第 4 节。
2. **身份网关 trp** 对 `/ai` 前缀的授权（前缀匹配）——否则整条链路拿不到身份 Cookie。
3. **防火墙**：40.44 → 70.37:8090 放通；**8090 不要对客户端网段开放**（Key 身份 Cookie
   本身就是凭据，谁能把请求送到网关，谁就能成为那个用户）。

配好后量一次（这一步专治"本机全绿、浏览器里不行"）：

```bash
bin/mt.sh mount-check https://officeai.301.avic:496/ai/harness/ --key-user liuy_1
```

`--key-user` 会模拟身份网关注入的 Cookie 走完整条链路，期望 **16 项全绿**，其中包含
"同一地址直接进入自己的 DSH"与"查询参数里的用户名不作数"。若拿到 403「这个入口没有开启
Key 登录」，说明网关看到的来源地址不是 `MT_KEY_LOGIN_FROM` 里那个：

```bash
grep key-login-untrusted-source logs/access.jsonl | tail -1   # 里面的 source 就是要填的地址
```

## 8. 日常运维与回退

### 8.1 备份

```bash
bin/mt.sh backup                     # → backups/dsh-mt-<UTC>.tar.gz，保留最近 7 份
bin/mt.sh restore backups/dsh-mt-<UTC>.tar.gz    # 现有数据先挪到 restore-aside-*/，不会删
```

装了定时备份容器（`mt-backup`）后无需手工跑；`doctor` 会报最近一次备份的时间。

### 8.2 更新前端/运行时镜像（离线）

包里的 `overlay/` 是前端覆盖层，配合载体镜像可以离线重建运行时镜像：

```bash
bin/publish-and-verify.sh overlay/image-overlay-<时间戳>.tar.gz --switch
```

它会以 `MT_BASE_IMAGE`（载体）为底打出新镜像、核对镜像内前端哈希与覆盖层一致、切换租户并跑 `doctor`。
要回退：把 `.env` 的 `DSH_IMAGE` 改回上一个标签 → `bin/mt.sh up`（旧镜像仍在本地）。

### 8.3 增删租户与吊销

```bash
bin/mt.sh add-batch tenants.csv --derive-id      # 追加新租户（已存在的会报错停下，不会重复建）
bin/mt.sh remove <租户>                           # 停容器、摘注册表，数据留在 tenants/<租户>/
bin/mt.sh remove <租户> --purge                   # 连数据一起删
bin/mt.sh passwd <租户> <用户名>                   # 改口令并立即吊销该用户所有会话
bin/mt.sh kick <租户> [用户名]                     # 只吊销会话（丢笔记本的常见情形）
```

### 8.4 紧急停

```bash
bin/mt.sh down          # 停全部容器（保留数据与配置）
```

### 8.5 加一台节点（把租户放到另一台机器上）

包里的 `bin/node-install.sh` 就是这一步，可重复执行。目标机需要先有部署目录（把离线包装一遍
`install-offline.sh --dest <同一路径>`，或从控制面同步同一份代码）与那三个镜像。

```bash
# ① 节点上接线（会写 .env 的角色、取回控制面的密钥与 CA、拉一份注册表、放行网关访问 3199）
bin/node-install.sh --node node2 --control-plane https://<控制面>:8090 \
  --fetch-from <控制面地址> --allow-from <主网关地址>,<备用网关地址>
bin/mt.sh up && bin/mt.sh agent up

# ② 控制面上登记一个住在它上面的租户（容器由那台机器创建）
bin/mt.sh add gamma2 --user gina --node node2
bin/mt.sh runtimes                     # 等 15 秒左右，应出现 gamma2 -> node2

# ③ 该节点自己的体检与备份
ssh <节点> 'cd <部署路径> && bin/mt.sh doctor && bin/mt.sh backup'
```

三个容易踩的点：**3199 要放行**（只给网关地址，不是整个网段；漏了就是登录 502
`EHOSTUNREACH`）；**控制面重建过 `state/keys.json` 之后所有节点要重跑一次取密钥**（否则注册
401，表现为"控制面上的租户一直没注册"）；**每台承载租户的机器各自出一份备份**（`bin/backup.sh`
只打本机租户，控制面的 `doctor` 会把不在本机备份里的租户点名）。

要把一个租户搬到另一台节点：`bin/mt.sh move <租户> --to <节点>`（停源端 → 搬数据 → 改注册表 →
目标机 `up`；实测 42 秒，期间该租户不可用）。回滚：`bin/mt.sh registry set-node <租户> <原节点>`
再在原节点 `up`（源端数据目录保留着）。

### 8.6 控制面高可用（备用网关 + 入口 nginx）

```bash
# ① 备用网关（可以同时是它自己的一个节点：--node；不带 --node 则只做备用网关）
bin/node-install.sh --standby --node node3 --control-plane https://<主网关>:8090 \
  --fetch-from <主网关> --allow-from <主网关>,<本机>
bin/mt.sh up
bin/mt.sh ha-sync --from <主网关> --install-timer     # 每 60 秒拉一次状态

# ② 承载租户的每台机器（含主网关那台）放行备用网关访问 3199
bin/mt.sh agent allow <备用网关地址>

# ③ 入口机 nginx：把两台的 8090 配进 upstream（片段见 ha/nginx.conf），reload
```

`ha-sync` 同步 `tenants.json` 与 `state/{session.key,keys.json,registry.key,register.key,ops.key,
admin.json,admin.key,runtimes.json,bandwidth.json,quota.json,tls}`；**不同步 `logs/`**，所以切换
之后审计历史分成两段。`runtimes.json` 同步过来后备用网关**自己会重新加载**（网关 watch 这个
文件），不需要重启容器。

实测（三台 VM，2026-10-11）：停主网关 → 入口 0.28 秒恢复、已登录用户不需要重新登录、远端租户
照常；启动主网关 → 0.51 秒回切。切换期间不可用的是**各租户的专属入口端口**（只在主网关开）。

## 9. 故障对照表

| 现象 | 先看这里 |
|---|---|
| `docker-compose build` 报 `failed to resolve source metadata` | BuildKit 在拉公网元数据。本部署一律 `DOCKER_BUILDKIT=0`（`bin/mt.sh up` 已内置） |
| 租户登录后 503 | 该租户运行时没注册：`bin/mt.sh runtimes`，然后 `bin/mt.sh register <租户>` |
| 入口页打得开，点登录没反应 | 控制台页面脚本没解析：`bin/mt.sh doctor` 的"控制台页面"一节会报 |
| 登录页没有 Key 按钮 | `.env` 没配 `MT_KEY_LOGIN_FROM`，或改了没 `bin/mt.sh up`；`doctor` 的"Key 免口令登录"一节会报 |
| Key 登录 403 | 请求不是从信任地址来的（客户端直连了 8090，没走入口机） |
| 页面说"未检测到有效的 Key 身份" | 本机没 Key／trp 没为这个前缀注入 Cookie（F12 看请求头有没有 `Cookie:`）／用户名不在租户注册表里 |
| 模型调用 401 或网关起不来 | `MT_UPSTREAM_API_KEY` 没填（留空时模型网关故意拒绝启动） |
| 模型调用超时但宿主能 curl 通 | 容器出网路径：`bin/mt.sh doctor` 的"租户出网"一节 |
| 界面流式输出中途断 | 入口机 nginx `proxy_read_timeout` 还是默认 60s → 放宽到 3600s |
| 反复刷新后登录报 429 | 限流：Key 登录 20 次带身份的失败锁 10 分钟，成功一次即清零；口令登录另有独立预算 |
| 磁盘吃紧 | `bin/mt.sh doctor` 的磁盘与租户用量；旧备份用 `bin/mt.sh backup` 的保留份数控制 |
| 某台节点的租户一直没注册 / 重启后入口一直 303 | 那台节点上的注册密钥与控制面不一致：`bin/node-install.sh --fetch-from <控制面>` 重取；控制面 `doctor` 会点名"注册密钥被拒过" |
| 远端租户登录 502 `connect EHOSTUNREACH <节点>:3199` | 节点没放行网关访问它的 3199：`bin/mt.sh agent allow <网关地址>`；节点侧自查 `doctor` 的"防火墙与网络"一节 |
| 切到备用网关后一部分租户 502 | 那些租户住在备用网关连不到的机器上（`agent allow` 漏了备用网关），或它们的端点还是容器 bridge 地址（老的注册记录：`bin/mt.sh up` 会重新按 `<主机>:3199/proxy/<租户>` 注册） |
| 备用网关上的"就绪"数不对 | 它的 `runtimes.json` 还没同步（`bin/mt.sh ha-sync --from <主网关>`），或它连不到那些节点 |

### 10.3 把这个包再复制给别的机器

目标机导完镜像之后，它自己也能打包（`bin/make-offline-bundle.sh` 就在包里）：

```bash
bin/make-offline-bundle.sh --payload /tmp/clean-deploy --overlay overlay/image-overlay-<时间戳>.tar.gz \
  --out /data1 --volume-size 1500M --commit <git sha>
```

`--payload` 必须是干净副本（不含 `.env`/`state/`/`tenants.json`）：脚本会拒绝把运行实例打进包。

**同一台机器上再跑第二套**（演练、测试）时，除了 `--dest` 换目录，还要照《从零重建手册.md》
开头那五项把配置全部错开——容器名前缀、网络名、网桥名、三个监听端口，以及**租户的专属入口端口**
（新注册表默认还是从 8091 起，会和已有部署的专属端口撞车，控制面会因 `EADDRINUSE` 起不来；
用 `bin/mt.sh add-batch … --no-edge-port` 或显式给 `--edge-port`）。

### 10.4 内置插件在离线环境下的运行时依赖（实测）

插件代码全部在运行时镜像里（本机构建的 330 个包的 `lib/` 覆盖层），**不需要联网下载任何东西**。
容易被误认为"缺依赖"的几类，逐条给实测结论：

| 能力（插件） | 运行时依赖 | 离线结论 |
|---|---|---|
| 文件搜索 grep/glob（`tool-fs-search`） | 随 npm 包发布的 ripgrep 二进制 | **镜像里就有**：`…/node_modules/@vscode/ripgrep-linux-x64/bin/rg`，实测 `rg --version` = 15.0.0 |
| 终端/伪终端 | node-pty 预编译 | **在**：`node-pty/prebuilds/linux-x64/pty.node`（**不需要 tmux**） |
| 图片与附件、FFI | sharp、koffi、node-addon-system | **都是 linux-x64 版，在** |
| 会话全文检索 | `node:sqlite`（Node 22 内置） | 在（默认 `openAt: never`，不启用就不开） |
| 命令执行（bash 工具） | bash、coreutils、git | 在（镜像里都有） |
| 沙箱 | bwrap → Landlock | 包里带了一个 47 KB 的 bubblewrap（`deploy/sandbox-debs/`），安装脚本把它打进派生镜像（`<标签>-sandbox`）。**容器里默认仍走 Landlock**：DSH 自带的 bwrap 探针不建用户命名空间，而容器没有 `CAP_SYS_ADMIN` 时建不出来（实测 `Creating new namespace failed`）。要让 bwrap 起来得用它的用户命名空间形式，先跑 `bin/sandbox-check.sh` 确认，再加 `MT_SANDBOX_BWRAP=1`；想更省事也可以接受 Landlock（默认就是这样）。 |
| 网页抓取/搜索（`web-fetch` / `web-search-deepseek`） | 公网、DeepSeek 搜索服务 | 离线**用不了**（不是插件坏，是没网可连）；而且出口代理**拒绝私网地址**，内网 URL 同样取不到 |
| 从 npm 装插件（`plugin-manager`） | npm registry | 离线用不了（只在有人主动装插件时才涉及） |
| 遥测（OTEL） | 上传端点 | web profile 里 desktop 专用行已 `disabled`；会话遥测默认只在用户显式点"反馈"时上传。要彻底关掉：在 `model.env` 里加 `DSH_TELEMETRY_DISABLED=1`（该文件会注入每个租户容器） |

实测旁证：现网那套的租户跑了几天，出口代理日志里**没有任何租户主动外连**，租户容器的
TCP 连接只有到本栈网关与模型网关的——也就是说，插件不会在后台偷偷访问互联网。
